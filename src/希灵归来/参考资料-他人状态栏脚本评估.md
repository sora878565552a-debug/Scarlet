# 他人状态栏脚本审阅与改版评估

审阅对象：`酒馆助手脚本-re0.json`（Re:0 星魂状态栏 re0-eidolon-ui v2.0.0），4389 行 / 约 18.8 万字符，形态为酒馆助手脚本。仅审阅，未改动本卡任何文件。

## 一、它是什么

一套**全屏浮层式**状态栏，不是嵌在楼层里的小面板。结构如下：

| 模块 | 行数 | 职责 |
|---|---|---|
| 00-config | 72 | 节点定义、能量条定义、资源地址、音乐库配置 |
| 01-util | 130 | 取值与容错工具 |
| 02-model | 394 | `stat_data` → 视图模型（Re:0 状态协议 v2） |
| 03-portraits | 281 | 立绘上传与管理 |
| 04-music | 215 | 音乐播放器 |
| 05-styles | 785 | 全部 CSS，约 500 行选择器，`re0-` 前缀 |
| 06-starfield | 188 | Canvas 星幕：星云渐晕 + 远近星层 + 缓升金尘 |
| 07-orb | 222 | 可拖拽的入口小球，位置存 localStorage |
| 08-shell | 499 | 浮层外壳、轨道节点环、节点图标与连线 |
| 09-ring | 181 | 环形节点布局与动画 |
| 10-details | 308 | 详情条目渲染（片段、键值、进度条、人物行） |
| 11-pages | 790 | 各类页面：生命体征、人物、循环、音乐、立绘 |
| 12-boot | 314 | 启动、MVU 数据读取链、事件监听 |

## 二、技术上可以接上的部分

**它的数据来源是标准 MVU**：`12-boot` 里是 `getVariables({type:'message'})` → `Mvu.getMvuData` 的读取链，并带 `waitForMvu` 兼容回退与 `lastGood` 缓存。也就是说，它读的确实是 `stat_data`，**跟我们的变量系统同源，不需要换框架**。

**它的工程习惯值得学**：工具层做了大量容错（`asRecord` / `asNumber` / `knownText` / `clampMeter`），模型层是纯逻辑无 DOM，外壳与页面分离。这套分层比多数同类脚本干净。

## 三、无法直接沿用的部分

**数据模型完全是另一套协议。** 它读的是：

- 世界：`当前时间.规范日期／时段`、`当前地点.国家／地区／场所`、`环境.天气／光照`、`危机等级`、`动向`、`势力态势`
- 主角：`姓名`、`角色类型`、`门状态`、`门负荷`、`魔女余香`、`战力等阶`、`能力.加护／权能／魔法／精灵术`、`伤势`、`异常状态`
- 轮回：`世界重启次数`、`存档点`、`菜月昴死亡记录`、`死亡回归`

我们的变量是 `普通矿物／导能晶体／高密度矿石／普通能量／幽能／设施状态`。**两者交集为零**——不是映射不齐，是根本不指同一类东西。

**界面隐喻与目标不符。** 它的六个节点是「世界时空／主角状态／轮回／人际羁绊／事件与线索／行囊资产」，配星场、金尘、魔法阵、立绘。你要的是舰船主控台——这套的视觉语言需要整体替换，只改配色不够。

**它依赖原作者的外部资源。** 立绘、音乐、节点图标都从 `raw.githubusercontent.com/1798547983tt/re0/...` 拉取。直接沿用等于替对方承担带宽，且对方一旦改动或删除，界面就会缺图。**这是授权层面的问题，不只是技术问题。**

**体量与我们需求不匹配。** 其中音乐播放器（215 行）、立绘上传（281 行）我们完全用不到；`05-styles` 的 785 行里大部分服务于立绘与节点视觉。

## 四、改造工作量估算

| 模块 | 处置 | 说明 |
|---|---|---|
| 00-config | **重写** | 换成舰船设施节点与资源定义 |
| 01-util | 沿用 | 通用工具，无 Re:0 依赖 |
| 02-model | **重写** | 改为读取我们的六项变量 |
| 03-portraits | 删除 | 无立绘需求 |
| 04-music | 删除 | 无音乐需求 |
| 05-styles | **重写** | 从星魂视觉改为主控台视觉 |
| 06-starfield | **重写** | 改为控制台背景（扫描线／网格／状态点） |
| 07-orb | 沿用 | 拖拽入口可留，换图标即可 |
| 08-shell | **重写** | 节点从六类资讯改为设施与资源分区 |
| 09-ring | **重写** | 环形布局不适合设施清单 |
| 10-details | 部分沿用 | 键值／进度条可留 |
| 11-pages | **重写** | 页面内容全部不同 |
| 12-boot | 基本沿用 | 只需改数据适配层 |

结论：**约六到七成需要重写**。真正能省下的主要是启动与读取链、工具层、以及浮层与拖拽的交互骨架。

## 五、建议

**建议不直接改版这份脚本，而是新建一个舰船主控台状态栏**，在思路上吸收它三点做法：

1. **悬浮入口 + 全屏浮层**，比嵌在楼层的面板更适合展示多项设施；
2. **节点／分区图**，点开看细节，天然适合「设施清单 → 单设施详情」；
3. **Canvas 背景**，可改为控制台风格（暗底 + 网格 + 扫描线 + 状态点），并做成可关闭。

这样做的代价是重写，但换来三件东西：一是不背 18.8 万字符的他人代码与对方的外部资源依赖；二是界面与我们的 `设施状态` 变量天然对齐；三是全部代码可维护、可继续扩展。

**若作者坚持要改这份脚本**，我可以按上表逐模块改造，但需要作者确认一件事：**是否接受继续依赖原作者的 GitHub 资源地址**（节点图标等）。若不接受，就得连图标资源一起重做，那样与新建的成本已经相差不大。

## 六、附带发现（对我们有用）

- 它把**入口做成可拖拽的小球并记忆位置**，这个交互模式值得保留。
- 它对 `stat_data` 做 **`lastGood` 缓存与 `waitForMvu` 回退**，比直接读取更稳；我们的 `defineMvuDataStore` 已有类似机制，但可以补一个"上次有效值"兜底。
- 它的详情渲染支持**片段折叠、键值对、带正负的进度条**，其中「键值对 + 进度条」正适合我们显示矿物数量与能量。
